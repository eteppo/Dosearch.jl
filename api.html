API reference

Dosearch.Dosearch — Module
Dosearch

Identification of causal effects from multiple, possibly incomplete, observational and experimental data sources by a search over do-calculus and probability manipulations. A Julia port of the R package dosearch (Tikka, Hyttinen and Karvanen, 2021, Journal of Statistical Software 99(5), doi:10.18637/jss.v099.i05).

The main entry point is dosearch.

using Dosearch brings the names of normal usage: dosearch, DosearchProblem, latex, typst, maximal_identifiable_graphs, maximal_identifiable_graph, BidirectedPair, LatentCause, confounding_candidates and with_candidates. The other names below are public but not exported: write Dosearch.CausalGraph, or import them with using Dosearch: CausalGraph.

Identification

Dosearch.dosearch — Function
dosearch(data, query, graph; kwargs...) -> DosearchResult
dosearch(problem::DosearchProblem; kwargs...) -> DosearchResult

Identify the causal query from the input distributions data in the causal model graph, by a search over do-calculus and probability manipulations (Tikka, Hyttinen and Karvanen, 2021). The graph is either a DAG with latent confounders or a labeled DAG (LDAG) with context-specific independences (Tikka, Hyttinen and Karvanen, 2019). This is a port of dosearch of the R package of the same name, and gives the same formulas.

Syntax

data lists the input distributions, one per line, as a string or a vector of strings. A distribution is written p(A|do(B),C): A, B and C are comma separated variable names, and both the conditioning variables C and the do-operator are optional (p(A|C,do(B)) is also allowed). For example

data = """
    p(z|do(x))
    p(w,y|do(z,x))
    p(w,y,x|z)
"""

A distribution can also be given as a NamedTuple of variable roles: 0 for the left-hand side, 1 for intervened and 2 for conditioning variables, so (y = 0, x = 1) is p(y|do(x)).

query is the target distribution in the same syntax.

graph has one edge per line: x -> y for a directed edge and x <-> y (or x -- y) for a bidirected edge, that is, an unobserved common cause of x and y. The parts of an edge are separated by whitespace.

LDAGs

A graph with edge labels is an LDAG. A label is a comma separated list of value assignments of other parents of the child, and the edge vanishes in the context that matches it. An edge that vanishes in several contexts is listed once for each (or, as in the R package, with the labels separated by ;):

graph = """
    X -> Y : A = 1
    Z -> Y : A = 0
    Z -> Y : B = 1, C = 0
"""

LDAGs have no bidirected edges: latent variables are explicit nodes that do not appear in the data. Interventions are explicit intervention nodes whose names start with I_, such as I_X -> X, and distributions condition on them instead of using the do-operator: p(Y|X,I_X=1). In general, variables in distributions of an LDAG can be assigned 0 or 1.

Values

For problems built in code, the inputs can be Julia values instead of text: data a P or a vector of them (mixed with text if needed), query a P, and graph a CausalGraph.

Keyword arguments

Model:

  • transportability: comma separated transportability nodes, which mark the discrepancies between domains, or a collection of their names.
  • selection_bias: comma separated selection bias nodes, or a collection of their names.
  • missing_data: comma separated missing data mechanisms r_x : x, where r_x is the response indicator of x, or pairs "r_x" => "x". The proxy variable x* of x is added automatically. A response indicator can be fixed to the observed value in distributions as r_x = 1.
  • md_sym = "1": the value that marks an enabled response indicator.
  • context_vars: names of further context variables of an LDAG, besides those in the edge labels and those fixed to a value in the query or an input.
  • warn = true: warn about inputs that are valid but probably unintended.

Transportability, selection bias and missing data are only supported for DAGs.

Search:

  • heuristic = false: expand the most promising terms first instead of in the order they were found.
  • strategy: the SearchStrategy that orders the search, ScoreHeuristic() if heuristic = true and FoundOrder() otherwise.
  • improve = true: leave out redundant rules, and stop early when the query is trivially not identifiable.
  • rules: the rules to use, in order, as R rule codes or as Rules for DAGs and CsiRules for LDAGs. Defaults to default_rules and default_csi_rules.
  • time_limit = Inf: stop the search after this many seconds (checked before each term is expanded; 0 stops at once). R gives the limit in hours.
  • term_limit: stop the search once it has derived this many terms (input distributions included; see the field terms of the result), checked before each term is expanded. Unlike time_limit, the result does not depend on the machine.
  • cache = true: for LDAGs, reuse context-specific independences that were found to hold, as the R package does by default.

Output:

  • formula = true: compute the identifying formula and its derivation (see latex and typst).
  • draw_derivation = false: return the derivation as a DOT graph, in the field dot.
  • draw_all = false: draw every derivation step, not only the steps that lead to the query.
  • benchmark_rules = false: record the time spent in each rule.
  • verbose = false: print the steps of the search, to io = stdout.

Differences from the R package: times are in seconds, draw_all draws the steps in the order they were found, and up to 32 variables are supported in DAGs (R: 15) and 64 in LDAGs (R: 30). Edges of an LDAG that vanish in every context are left out of the contexts too; R keeps them there by mistake.

Examples

julia> r = dosearch("p(x,y,z)", "p(y|do(x))", """
           x -> y
           z -> x
           z -> y
       """);

julia> r.formula
"\\sum_{z}\\left(p(z)p(y|x,z)\\right)"
Dosearch.DosearchResult — Type
DosearchResult

The result of dosearch.

  • identifiable::Bool: whether the query was identified.
  • limit_reached::Bool: whether the search stopped at time_limit or term_limit before it could decide; the query is then not identified, but may be identifiable.
  • formula::Union{Nothing,String}: the identifying formula in LaTeX, in the notation of the R package, or nothing if the query was not identified or formula = false.
  • derivation::Union{Nothing,Derivation}: the Derivation of the formula, which latex and typst write out step by step (nothing if there is no formula).
  • dot::Union{Nothing,String}: the derivation as a DOT graph if draw_derivation = true (derivation in the R package).
  • time::Float64: seconds spent searching.
  • terms::Int: the number of terms the search derived, input distributions included (what term_limit limits).
  • rule_times::Vector{Float64}: seconds spent in each rule of rules if benchmark_rules = true.
  • rules: the rules that the search used, in order.
  • problem::DosearchProblem: the problem that was solved.

Dosearch.DosearchProblem — Type
DosearchProblem

Abstract type of validated identification problems: DagProblem and LdagProblem. DosearchProblem(data, query, graph; kwargs...) builds an LdagProblem if the graph has edge labels and a DagProblem otherwise. See dosearch for the syntax of the arguments.

Dosearch.DagProblem — Type
DagProblem(data, query, graph; transportability, selection_bias,
           missing_data, md_sym = "1", warn = true)

A validated causal effect identification problem in a DAG with latent confounders: identify the query from the input distributions data in the causal model graph. See dosearch for the syntax of the arguments.

The fields hold the problem in internal form: labels are the variable names by index, and data and query are Dist terms over those indices.

Dosearch.LdagProblem — Type
LdagProblem(data, query, graph; context_vars = String[], warn = true)

A validated identification problem in a labeled DAG: identify the query from the input distributions data in the LDAG graph. See dosearch for the syntax. context_vars names extra variables to treat as context variables, besides those that appear in edge labels and those fixed to a value in the query or an input.

In internal form, a term Dist over this problem has the left-hand side a, the right-hand side b, and the variables assigned to 0 in c and to 1 in d.

Graphs and distributions as values

Dosearch.CausalGraph — Type
CausalGraph(edges...)

A causal graph as a value: the same graph as the text syntax of dosearch, for building and combining graphs in code. The edges are

  • from => to, a directed edge, with names as strings or symbols;
  • BidirectedPair(x, y), an unobserved common cause of x and y;
  • LabeledEdge(from => to, assignments...), an edge of an LDAG that vanishes in a context;
  • a graph in the text syntax, or another CausalGraph, whose edges are included in order;
  • a collection or generator of edges.

Repeated edges are kept once. The order of the edges is kept: it fixes the numbering of the variables, and so the order in which formulas list them. Two graphs are equal if they have the same edges in the same order. string(g) is the graph in the text syntax, and g ∪ h contains the edges of both. Wherever a problem takes a graph, a CausalGraph can be given.

Examples

julia> using Dosearch: CausalGraph

julia> g = CausalGraph("x" => "y", "z" => "x", "z" => "y")
CausalGraph with 3 edges:
  x -> y
  z -> x
  z -> y

julia> g ∪ CausalGraph(BidirectedPair("x", "y"))
CausalGraph with 4 edges:
  x -> y
  z -> x
  z -> y
  x <-> y

julia> chain = CausalGraph("A$k" => "A$(k + 1)" for k in 1:3);

julia> print(chain)
A1 -> A2
A2 -> A3
A3 -> A4
Dosearch.LabeledEdge — Type
LabeledEdge(from => to, assignments...)

An edge of an LDAG that vanishes in a context: the assignments, pairs variable => value with the values 0 or 1, of other parents of to. LabeledEdge("X" => "Y", "A" => 1) is the line X -> Y : A = 1 of a graph. An edge with several labeled edges vanishes in each of their contexts.

Dosearch.P — Type
P(variables...; given = (), intervened = ())

A distribution as a value: P("y"; given = "z", intervened = "x") is p(y|do(x),z) in the text syntax of dosearch, for building inputs and queries in code. given and intervened take a name or a collection of names, as strings or symbols. A variable can be assigned a value by a pair name => value: 0 or 1 in an LDAG, as in P("Y"; given = ["X", "I_X" => 1]), and the symbol of an enabled missing data mechanism (md_sym, 1 by default) in a DAG, as in P("x*"; given = "r_x" => 1).

string(d) is the distribution in the text syntax. Wherever a problem takes its input distributions or its query, a P or a vector of them can be given.

Examples

julia> using Dosearch: CausalGraph, P

julia> P("y"; given = "z", intervened = "x")
p(y | do(x), z)

julia> dosearch([P("x", "y", "z")], P("y"; intervened = "x"), CausalGraph("x" => "y", "z" => "x", "z" => "y"))
\sum_{z}\left(p(z)p(y|x,z)\right)

Derivations

Dosearch.Derivation — Type
Derivation

How the search derived an identified query. Stored in the derivation field of a DosearchResult.

Written out, the derivation starts from the query and rewrites one term at a time by the rule that derived it, until only known terms remain. The last line is then the identifying formula. Each step names its rule. A do-calculus step also gives the d-separation that licenses it, in the mutilated graph of the rule. An LDAG step gives the context-specific independence instead.

latex(d) and typst(d) write the derivation for a document, and d displays as plain text. The keyword inputs = true continues the derivation past the terms that the formula keeps. Those terms are computed from an input distribution by probability manipulations alone, and the rewriting stops only at the input distributions themselves.

The fields are internal: the problem, the derivation's nodes of the search (node 1 is the query), the rewrite of each derived node and the identifying formula in the notation of the R package.

Markdown.latex — Function
latex(d::Derivation; inputs = false, labels = Dict()) -> String
latex(r::DosearchResult; kwargs...) -> String

The derivation d, or the derivation of the identified query of r, as a LaTeX align* environment (package amsmath). This adds methods to Markdown.latex. The first line is the query. Each following line rewrites one term and names the rule it uses in a second column; the last line is the identifying formula. Long derivations may need \allowdisplaybreaks to break across pages.

With inputs = true, terms computed from an input distribution by probability manipulations are rewritten too, down to the input distributions. labels maps variable names to LaTeX code that replaces the default: one letter as is, longer names in \mathit, the part after the first _ as a subscript and a trailing * as a superscript.

Examples

julia> r = dosearch("p(x,y,z)", "p(y|do(x))", """
           x -> y
           z -> x
           z -> y
       """);

julia> print(latex(r))
\begin{align*}
p(y \mid \mathrm{do}(x)) &= \sum_{z} p(y, z \mid \mathrm{do}(x)) && \text{marginalization} \\
&= \sum_{z} p(z \mid \mathrm{do}(x)) p(y \mid \mathrm{do}(x), z) && \text{chain rule} \\
&= \sum_{z} p(z) p(y \mid \mathrm{do}(x), z) && \text{rule 3: } (z \perp\!\!\!\perp x)_{\mathcal{G}_{\overline{x}}} \\
&= \sum_{z} p(z) p(y \mid x, z) && \text{rule 2: } (y \perp\!\!\!\perp x \mid z)_{\mathcal{G}_{\underline{x}}}
\end{align*}

Maximal identifiable graphs

Dosearch.maximal_identifiable_graphs — Function
maximal_identifiable_graphs(problem; candidates, formulas = false, heuristic,
                            improve, rules, time_limit, term_limit) -> MaximalGraphs
maximal_identifiable_graphs(data, query, graph; kwargs...)

All maximal sets of candidates that can be added to the model of problem while the query stays identifiable by dosearch, and all minimal sets that make it non-identifiable. The result is a vector of the maximal sets; see MaximalGraphs for its other fields. Build the problem with a set added with with_candidates.

candidates defaults to confounding_candidates: every latent confounder between a pair of variables that can be added. Candidates of other kinds, such as LatentCause, can be given instead. If the query is not identifiable in the original model there are no maximal sets, and the empty set is the only minimal non-identifiable set. With formulas = true, the identifying formula of each maximal graph is computed too. heuristic, improve and rules are passed to dosearch. The first maximal set is the one that maximal_identifiable_graph finds.

For an LDAG, a candidate adds a latent node with edges into its variables, which may be labeled (see LatentCause). The variables in the labels of the candidates are context variables in every search, including the one of the original model, so that larger sets of candidates cannot gain case distinctions; problem in the result is the problem with them.

time_limit (seconds) and term_limit (derived terms) limit each search, as in dosearch. A set whose search stops at a limit counts as non-identifiable and is reported as undecided. Every reported maximal set is still identifiable, but it may not be maximal. With term_limit the result is reproducible; with time_limit it depends on the machine, its load and the number of threads. The formulas are computed without the limits.

Limits pay off when some searches cost far more than the others. A limit that also stops searches that would identify the query makes the result coarse, since every superset of an undecided set counts as non-identifiable too. Adding confounding shrinks the space of derivable terms, so the search in the original model is a guide: set the limit above its terms or time (from dosearch(problem)).

The sets are found by dualize and advance (Gunopulos et al., 2003), which checks each maximal set and each minimal non-identifiable set of candidates once, plus the checks needed to extend sets to maximal ones. It relies on adding candidates never making a query identifiable, which holds for latent confounders: they only remove d-separations. A set is known to be identifiable without a search when all d-separations used by an earlier derivation of the query still hold, so most searches are of non-identifiable sets. Searches run on several threads when Julia has them (e.g. julia --threads=auto); the result does not depend on the number of threads.

Examples

In the chain x -> z -> y, the effect of x on y stays identifiable if x and y are confounded (by the front-door formula) or if z and y are confounded, but not both:

julia> graph = """
           x -> z
           z -> y
       """;

julia> maximal_identifiable_graphs("p(x,y,z)", "p(y|do(x))", graph)
2 maximal identifiable sets of 3 candidates:
  y <-> z
  x <-> y
2 minimal non-identifiable sets:
  x <-> z
  y <-> z; x <-> y

Confounding x and z alone, or y and z together with x and y, makes the effect non-identifiable.

Dosearch.maximal_identifiable_graph — Function
maximal_identifiable_graph(problem; candidates, heuristic, improve, rules,
                           time_limit, term_limit) -> Union{Nothing,Vector{<:Candidate}}
maximal_identifiable_graph(data, query, graph; kwargs...)

One maximal set of candidates that can be added to the model of problem while the query stays identifiable, found greedily: each candidate is added in turn if the query stays identifiable. Earlier candidates are preferred, so the order of candidates decides which maximal set is found. Needs at most one search per candidate. Returns nothing if the query is not identified in the original model. See maximal_identifiable_graphs for the arguments; with a limit, a candidate whose search stops at it is left out, so the set may not be maximal.

Dosearch.MaximalGraphs — Type
MaximalGraphs{C}

The result of maximal_identifiable_graphs: the maximal identifiable sets of candidates of type C. It is a vector of these sets, and also has the fields

  • maximal::Vector{Vector{C}}: the maximal sets of candidates that can be added while the query stays identifiable;
  • minimal_nonidentifiable::Vector{Vector{C}}: the minimal sets of candidates that make the query non-identifiable. Every set that contains none of them (and none of the undecided sets) is identifiable, and no other set is;
  • undecided::Vector{Vector{C}}: the minimal sets whose search stopped at time_limit or term_limit. They count as non-identifiable, so if there are any, the maximal sets are identifiable but may not be maximal, and some minimal non-identifiable sets may be missing;
  • formulas::Vector{String}: the identifying formula with each maximal set added, if formulas = true was given, and empty otherwise;
  • candidates::Vector{C} and problem::DosearchProblem: the inputs;
  • searches::Int: the number of searches that were needed.

Each set lists its candidates in the order of candidates.

Dosearch.Candidate — Type
Candidate

Abstract type of the additions to a causal model that maximal_identifiable_graphs chooses from, such as BidirectedPair.

Adding candidates to a model must only add paths to the graph, so that a query that is identifiable with a set of candidates stays identifiable with any subset of it. To add a kind of candidate, define Dosearch.confounded_pairs(problem::DagProblem, candidate), which returns the bidirected edges that the candidate adds as pairs of variable indices, and Dosearch.latent_edges(problem::LdagProblem, candidate), which returns the edges of the latent node that the candidate adds to an LDAG.

Dosearch.BidirectedPair — Type
BidirectedPair(x, y)

The candidate that adds the bidirected edge x <-> y, i.e. a latent common cause of the variables named x and y. The pair is unordered. In an LDAG, which has no bidirected edges, it adds a latent node U_x_y with the edges U_x_y -> x and U_x_y -> y.

Dosearch.LatentCause — Type
LatentCause(variables...; labels = [])
LatentCause(variables; labels = [])

The candidate that adds a latent common cause of all the named variables: a bidirected edge between every pair of them, added together. LatentCause("x", "y") adds the same edge as BidirectedPair("x", "y"). The order of the variables does not matter.

In an LDAG, it adds a latent node with an edge into each of the variables. labels gives some of these edges a label, as pairs child => label in the syntax of the graph: LatentCause("x", "y"; labels = ["y" => "a = 1"]) is a latent cause of x and y whose edge into y vanishes where a = 1. The variables of a label must be parents of the child. The search for maximal graphs treats them as context variables throughout (see maximal_identifiable_graphs). An edge into a variable with an intervention node I_x also vanishes where I_x = 1, like the other edges into an intervened variable. Labels are not supported for DAGs.

Dosearch.confounding_candidates — Function
confounding_candidates(problem) -> Vector{BidirectedPair}

Every bidirected edge that can be added to the model of problem: all pairs of variables that are not already bidirected, except pairs with a transportability node or a missing data proxy. The pairs are ordered by the internal variable numbering.

confounding_candidates(problem::LdagProblem) -> Vector{BidirectedPair}

Every pair of variables of the LDAG of problem that can get a latent common cause, i.e. all pairs without intervention nodes, ordered by the internal variable numbering.

Dosearch.with_candidates — Function
with_candidates(problem, candidates) -> DosearchProblem

The problem whose causal model has the candidates added.

Internals

Dosearch.VarSet — Type
VarSet

An immutable set of variable indices in 1:64, stored as a bitmask.

VarSet supports the usual set operations (∪, ∩, setdiff, ⊆, in, isempty, length) and iterates over its elements in increasing order. Construct one from a collection of indices, as in VarSet([1, 3]) or VarSet(1:3), or from a raw bitmask with VarSet(mask::UInt64).

Dosearch.Dist — Type
Dist(a, b, c, d)

A distribution term $P(A \mid do(C), B \setminus C)$ over variable indices.

  • a: the variables on the left-hand side.
  • b: every variable on the right-hand side, both conditioning and intervened variables, so c ⊆ b.
  • c: the intervened variables, inside do(⋅).
  • d: the missing data mechanisms (response indicators) that are enabled, i.e. fixed to the observed value, in this term.

Dist is an immutable value type and can be used as a Dict key.
